# Review and refactor proposal — latency, output speed, call-type quality

Date: 2026-09-23. Scope: the v4 codebase as committed at `79ca7a6`. Method: three independent
read-only code reviews (core Stop→first-token path, frontend delta→pixels path, prompt/quality
design), cross-checked against the code and the current Claude API reference. Nothing in this
document has been measured on the wire yet; every millisecond figure is an estimate from
reading the code and is marked as such. The first work item is therefore instrumentation.

## 0. Summary

The pipeline is sound: nothing local on the Stop path costs more than ~25 ms in total. Almost
all of the user-visible wait is two network waits that run **one after the other**:

| Segment of "Stop → first word on screen" | Estimated today | Notes |
|---|---:|---|
| Audio drain (WASAPI thread join, resampler/framer flush, relay) | 2–10 ms | fine |
| Deepgram flush: CloseStream → final Results → Metadata → Close frame | **200–1500 ms** | we only accept the *Close frame* as "done" |
| Prompt + request build, HTTP send | 1–3 ms, or 60–300 ms if the pooled connection is gone | pool idle is 10 s; recordings are longer than that |
| Anthropic time-to-first-token (Haiku 4.5) | **300–1500 ms** | prompt cache almost never hits (see F1) |
| Event pump → Tauri Channel → React → DOM | 2–20 ms | one wasted frame per delta (F5) |

Three findings are defects rather than tuning opportunities and should be fixed first:

- **F1 — Prompt caching is silently inactive for most profiles.** Haiku 4.5 will not cache a
  prefix shorter than **4096 tokens**; a typical `cached_prefix` (role ≈ 250 tokens + a two-page
  resume ≈ 1300 + a JD ≈ 600) is ≈ 2–3k tokens. The request is built correctly
  (`crates/llm/src/anthropic.rs:52-59`), the cache just never engages, and nobody can see that
  because `message_start.usage` is discarded (`anthropic.rs:157`).
- **F2 — The "pre-warmed pooled connection" is dead for any recording longer than 10 s.**
  `TRANSPORT_POOL_IDLE_TIMEOUT` is 10 s (`crates/contract/src/config.rs:27`), so the connection
  warmed at Record is closed before Stop. The re-warm at Stop is a plain HTTP/1.1 GET that races
  the real request (reqwest is built without `http2`, root `Cargo.toml:38`), so the worst case
  is a full TCP+TLS handshake on the critical path.
- **F3 — The Deepgram wait is longer than it needs to be.** `SttEvent::Flushed` is raised only
  when the server sends its Close frame (`crates/stt/src/lib.rs:318-348`). Deepgram's
  `{"type":"Finalize"}` message + the `from_finalize` flag on Results would let the session take
  the transcript the moment the last Results frame arrives, and would also allow the socket to
  be reused. Neither exists in the client (`crates/stt/src/parse.rs`).

The rest of the document ranks the refactors in four tracks: **A** core latency, **B** render
and perceived speed, **C** answer quality per call type (stack packs), **D** measurement.
Track D items are prerequisites: every other item is justified by an estimate that D turns into
a number.

## Track A — core latency (Stop → first token)

Ranked by expected saving ÷ risk. Savings are estimates until D3 runs.

**A1. Warm the Anthropic prompt cache at Record time (`max_tokens: 0`).**
*What:* when Record (or Ask) is pressed, POST the identical request shape — same model, same two
system blocks, a fixed dummy user message — with `max_tokens: 0` and `stream: false`. The API
runs prefill, writes the cache entry, returns `content: []` immediately. The real request at Stop
then reads the cache. This also replaces the `GET /v1/models` warm-up: it is a real POST over the
same connection, so the TLS session and pool slot are exercised by an actual request.
*Why:* prefill of a 3–5k-token prefix is a measurable part of TTFT; a cache read skips it.
Recording lasts seconds, comfortably longer than the "entry becomes readable once the first
response starts" window. Cost: one cache write (1.25× input) per Record when the entry is cold,
then ≈ 0.1× reads; during a call answers arrive < 5 min apart so the entry stays warm.
*Caveat (F1):* this does nothing on Haiku 4.5 unless the prefix is ≥ 4096 tokens. See A2/C1.
*Risk:* low. Errors must stay silent (never surface a warm-up failure as a session error).
Files: `crates/llm/src/anthropic.rs` (add `prewarm_cache(prompt, key)`), `crates/session/src/actor.rs`
(call it at install instead of `prewarm()`), contract `AnswerProvider` (add a default-noop method).

**A2. Decide the caching floor deliberately.** Two honest options, measured with D1/D3:
- (a) Keep Haiku 4.5 and let the C-track stack pack + exemplars (~400 tokens) plus a real resume
  push typical prefixes past 4096. Do **not** pad the prefix with filler just to cross the line —
  padding costs prefill time on every cache miss and adds nothing to answer quality.
- (b) Offer Claude Sonnet 5 for technical/system-design calls (see C6): its minimum cacheable
  prefix is 1024 tokens, so caching engages for essentially every profile. Sonnet's TTFT is
  higher than Haiku's; whether the cache read offsets it is exactly what D3 measures.

**A3. Keep the LLM connection alive through the recording.**
*What:* raise `TRANSPORT_POOL_IDLE_TIMEOUT` from 10 s to 90 s and re-issue a throttled warm-up
every ~8 s while a session is recording (cheap; it is a GET or a HEAD, no key). Enable reqwest's
`http2` feature so the warm-up and the real request share one connection and the pool waits for
an in-flight connect instead of opening a second socket.
*Why (F2):* today the connection is gone by Stop for any recording over 10 s, and the Stop-time
re-warm races the real request over HTTP/1.1. Expected saving: 0 in the lucky case,
60–300 ms when the Deepgram flush is short or the network is slow.
*Risk:* low. `read 75 s > total 60 s` still holds. Files: `crates/contract/src/config.rs`, root
`Cargo.toml` (reqwest `http2`), `crates/session/src/actor.rs` (periodic warm while recording).

**A4. Deepgram `Finalize` + `from_finalize`; treat the final Results as the end.**
*What:* on Stop send `{"type":"Finalize"}` after the last frame; raise `Flushed` when a Results
frame with `from_finalize: true` (or the next `is_final` after Finalize) arrives; close the
socket in the background afterwards. Keep the current CloseStream/Close path as the fallback
behind the existing 5 s cap.
*Why (F3):* the session currently waits for Metadata + Close after the transcript is already
known. Expected saving: the Results→Close gap, 10–100 ms (unknown, measure).
*Risk:* medium — needs a fallback if `from_finalize` never arrives; the `Flushed`-then-silence
invariant (§5.5) must be kept. Files: `crates/stt/src/{lib,parse}.rs`, `crates/session/src/actor.rs`.

**A5. Speculative answer request at Stop (the big one, gated on data).**
*What:* at Stop acceptance, immediately build and send the LLM request with the transcript as it
stands (finals + current interim) while the drain and Deepgram flush proceed. When `Flushed`
arrives, compare the final transcript with the speculative one after normalisation (case,
punctuation, whitespace): equal → keep the running stream; different → abort it and send the
real one. The transcript shown to the user must always be the one actually sent.
*Why:* removes the whole Deepgram flush (200–1500 ms) from the critical path whenever the tail
did not change — and Deepgram's interim is usually complete once the speaker has stopped.
*Cost:* on a mismatch you pay for two requests (the first is cut early; with Haiku this is
cents per day). *Risk:* medium-high — a new state in the session machine, a new invariant test
set (the speculative stream must never paint a delta before the transcript is confirmed, or
must paint under a visible "confirming…" state — pick one and test it), and interaction with
retry-once. **Do not build this before D3 reports the match rate; if the tail changes in
> 30 % of stops the saving evaporates.**

**A6. Smaller items (do opportunistically):**
- Build the cached-prefix JSON bytes at Record, not at Stop (`actor.rs:739-771`): 1–3 ms with a
  large profile; also removes three of the four 200 kB copies on the Stop path.
- Cache the rustls `ClientConfig` for the Deepgram connector (one `Arc`), so each connect stops
  rebuilding the root store: 1–5 ms CPU per Record, plus TLS session resumption.
- Cache the WASAPI device enumerator or use `IMMNotificationClient` instead of the once-a-second
  `CoCreateInstance` poll (`crates/audio/src/lib.rs:37`): removes a few ms of jitter if Stop
  lands mid-poll.
- Frames of 1024 samples (64 ms) instead of 2048: Deepgram is up to 64 ms less behind at Stop.
  The contract pins 2048 in tests; change `FRAME_SAMPLES` and the tests together, and send
  `audio:level` at the old cadence (coalesce two frames) so the UI rate is unchanged.
- Ask path: drop the connection warm-up (it fires microseconds before the real request and just
  opens a second socket); rely on A3's kept-alive connection.

**Not recommended:** a persistent Deepgram socket across sessions. It only helps the first
partial and a Stop pressed while still connecting (capture already starts before the socket
opens and pre-buffers), it needs per-session accumulator resets and stale-socket detection, and
idle-open billing is unclear. Revisit if D3 shows Stop-during-connect is common.

## Track B — render path and perceived speed

**B1. Commit the first delta synchronously; coalesce after it.**
`controller.ts:146-158` dispatches from inside a `requestAnimationFrame` callback; React 19
schedules that DefaultLane update in a later task, so the DOM lands one frame later than the
paint the rAF was aligned to. Flush the *first* delta of a session with `flushSync` (or
synchronously outside rAF) and keep per-frame coalescing afterwards. ≈ 16 ms off the first word
and off every delta. Risk: low; keep the one-paint-per-frame test.

**B2. Stop re-rendering the whole tree on every delta.**
`AppProvider.tsx:47-48` recomputes `selectView` into a new object per state change, so every
`useApp()` consumer (Header, StatusLine, controls, chips, history…) re-renders on each delta,
each `audio:level` and each 250 ms tick. Split the context: a stable `actions` context, a
slow-changing `view` context, and a streaming `entry` slice behind `useSyncExternalStore` with
per-slice equality (or `React.memo` the non-answer components). 5–10× less main-thread work per
frame on a low-memory laptop, which is exactly when frames get dropped. Risk: medium (broad but
mechanical). Also coalesce `audio:level` and `stt:partial` into the same rAF queue as deltas
(`controller.ts:161`) — terminal and control events stay immediate.

**B3. Reveal by sentence, not by token.**
Buffer the streaming tail and show completed sentences (or clause breaks on `,;:`) in full
opacity with the in-progress fragment dimmed. Eyes stop chasing a moving cursor; this is the
single biggest *perceived* speed win for someone reading aloud. Pair it with a
"say-this-first" line: render the first sentence as its own block at ~1.2× size (and ask the
model for a self-contained first sentence — C4). No animation, no transition.

**B4. Kill layout shifts during streaming.** Reserve the latency-chip slot
(`visibility: hidden` until metrics arrive), fix the Copy button's `min-width`, `flex-wrap:
nowrap` on `.panel__tools`, move notices/errors below the answer, and hide an unmatched
trailing `*`/`_`/backtick while streaming (tail-only transform; the cut-point property test is
unaffected). Measure first paint from a rAF inside the layout effect so it counts pixels, not
commit.

**B5. Reading typography for the prompter.** 48–55 ch column (68 ch today), line-height 1.6,
20–22 px default, bullets as short spoken chunks, anchor-top with a "▼ more" hint in the full
layout too (auto-scroll slides the line you are reading). Optional "read position" mode: Space /
Down advances a highlighted sentence, read sentences dim to ~55 %, the current one is kept at a
fixed eye line near the camera.

**B6. Incremental block parse.** `Markdown.tsx:50` re-parses the whole answer every frame
(O(n²) per answer). Cache the previous parse and re-parse from the start of the last block when
the new source extends the old one; memo list items. Cheap today (< 1 ms for 400 words) —
matters only for Detailed answers and Groq's token rate. Low risk; property test covers it.

## Track C — answer quality tailored to the call

The current technical prompt is correct but generic: the only stack signal is "prefer the tools
named in the focus section". It has no notion of seniority, no idea the transcript is speech
recognition ("Jango", "no JS"), no rule for multiple questions, and no numeric word budget.
The grounding split (technical facts need not come from the resume; experience claims must) is
right and should be kept.

**C1. Stack packs in the cached prefix.**
*Data model (additive, serde defaults):* `Profile.stack: StackSetting` = `auto | none | <StackId>`
with `StackId ∈ {javascript, typescript, react, node, python, django, dotnet, java_spring, sql,
aws, go, kubernetes}` and `Profile.seniority: SenioritySetting` = `auto | junior | mid | senior`.
Packs apply to `technical` and `system_design`; seniority also to `behavioral`.
*Placement:* role → stack pack → seniority → ASR alias line → resume/JD/focus/notes → grounding,
all inside `cached_prefix`. Stable per profile, so it caches; ~350–400 tokens per pack (a
one-pack-plus-exemplar block adds ≈ 1–3 ms of prefill on a miss and nothing on a hit). Keep the
total stack material ≤ ~600 tokens — past ~1k tokens of instructions, word-budget adherence
visibly degrades before cost does. Not in `style_suffix` (global, uncached) and not in
`user_message` (paid on every request).
*Auto-detection:* a pure `detect_stack(focus, jd, resume) -> Option<StackId>` over a fixed
keyword table (`crates/prompt/stacks/keywords.json`, `include_str!` in Rust, imported as JSON in
TS with a parity test). Weights focus ×3, JD ×2, resume ×1, word-boundary, case-insensitive,
threshold 3, ties by enum order, at most one primary + one secondary (e.g. react + typescript).
The profile editor shows the live result: "Auto (detected: Django)".
*Byte-stability:* with stack = none and seniority = auto-resolved-to-none the bytes are exactly
spec §8; existing snapshots stay green; new snapshots `technical.<style>.<stack>.<seniority>.txt`
plus a hash test on every pack string. Amend SPEC §8.
*Contract impact:* `Profile` gains two fields; `PromptInput` (pinned) gains
`stack: Option<StackId>, seniority: Option<Seniority>`; `eval::Profile`/`Fixture` gain the same.
TS regen via `cargo test -p callcore-contract`; two selects in `ProfileEditor.tsx`.
*Why this works:* a short curated block tells the model what an interviewer in that stack
actually probes, which vocabulary signals competence, and which misconceptions sink a
candidate — a generic "answer correctly" cannot. The exemplar fixes the *spoken* shape.

Drafted pack texts (168–169 words each) — see Appendix A. These are first drafts to be checked
by someone who interviews in each stack; the eval loop in C5 is how they get tuned.

**C2. Fix ASR errors at the source, not only in the prompt.** Pass the stack's term list to
Deepgram's Nova-3 key-term boosting (`keyterm` query parameter — verify the current name in the
Deepgram docs before wiring). Same keyword table, zero LLM tokens, and the transcript the user
*sees* becomes correct too. Keep the per-stack alias line in the prefix as the second line of
defence, plus one generic preamble sentence: "The transcript comes from speech recognition;
interpret misheard technical terms by sound."

**C3. Style suffixes with hard budgets.** brief ≤ 40 words, balanced ≤ 90, detailed ≤ 160,
stated in the suffix (kept under the fixture caps 60/150/260 so the eval enforces them). Leave
`max_tokens` at 1024 as the safety net; a per-style `max_tokens` would produce `truncated`
finishes. Fewer tokens is also the only "output speed" lever the app controls: token rate is the
provider's; answer length is ours.

**C4. Role-level rules (cheap, cached):**
- "Your first sentence must be a complete, correct answer the user can say on its own; details
  follow." (pairs with B3's say-this-first line)
- "If the transcript contains several questions, answer the last one unless it depends on an
  earlier one; if two were asked together, answer both briefly in order. Ignore filler."
- Technical grounding: "Mention employers, projects and numbers only if they appear in the
  resume; never invent metrics. If asked about experience the resume lacks, name the closest real
  experience and how you would approach it."
- Optional `Profile.answerLanguage` (default English keeps today's bytes).

**C5. Quality loop for the eval harness (build in this order):**
1. Prompt-byte snapshots per (call type × style × stack × seniority) + pack hash test — free.
2. Golden sets: 10 questions per stack in `fixtures.json` with `stack`, `seniority`,
   `mustMention`, `misconceptions` (forbidden claims like "JavaScript is multithreaded"), and an
   `asrVariant` ("Jango" spelling; the answer must say Django and never Jango).
3. Deterministic checks in `check_answer`: no markdown artefacts, first sentence ≤ 25 words,
   style budget, misconception substrings, resume-claim check (employer names / digits must
   appear in the resume).
4. Opt-in live runner under `--budget-usd`, recording TTFT, total, cache read/write tokens.
5. Opt-in LLM-as-judge with `claude-sonnet-5` (≈ $1.50 per full run): correctness 0–2,
   speakability 0–2, grounding 0–2, lead-sentence pass/fail, JSON out, diffed against the last run.

**C6. Model per call type — measured, not assumed.** Haiku 4.5 ($1/$5 per MTok) stays the
default everywhere: for recruiter, behavioral, sales and meeting calls the answer is judgement
and tone, and Haiku's TTFT is the product. For `technical` and `system_design` the answer is
often a fact (microtask vs `setTimeout` ordering; whether `prefetch_related` joins), and a wrong
fact said confidently on camera is worse than 300 ms. Offer an "Accuracy" option that maps
those two call types to `claude-sonnet-5` ($2/$10) with thinking off (thinking tokens delay the
first spoken word), same `max_tokens`, same two system blocks. Sonnet's 1024-token cache floor
means caching actually engages (A2b). Ship it *off* by default and publish the measured delta in
the settings copy ("Accuracy: ~+0.3 s to first word") once D3 has numbers. Contract impact:
`ProviderInfo.model` becomes a per-call-type map; the cache namespace changes with the model,
which is fine because a profile has one call type. Groq stays the "fastest" preset unchanged.
Do not use an Opus-tier model here: the latency budget is ~1 s and the questions do not need it.

## What not to do

- Don't pad the prefix to reach the cache floor (A2). Don't switch to Opus-tier models for
  interviews. Don't build A5 before measuring the match rate. Don't put the stack pack in
  `style_suffix` or `user_message`. Don't move to a persistent Deepgram socket on a hunch.

## Appendix B — correctness notes found on the way (not latency)

- Stop pressed during Deepgram connect keeps capturing until the socket opens, so audio after
  the press ends up in the transcript. Allowed by spec §4.7; worth a status line ("finishing
  connection…").
- The Ask-path connection warm-up is wasted (fires microseconds before the real request).
- A growing bullet list re-renders every item each frame (`Markdown.tsx:10-19`, no per-item memo).
- Hotkey stops start the visible-first-word clock only when `hotkey:toggle` reaches the page,
  so they under-count the core→page hop.
